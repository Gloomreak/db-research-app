# Методика экспериментов

## Сценарии

Генерация поддерживает 1 000, 10 000 и 100 000 задач. Seed по умолчанию — 42; применяется LCG `state = (1664525 * state + 1013904223) mod 2^32`. Вставка выполняется транзакционно. Замена данных затрагивает только выбранное хранилище и подтверждается пользователем.

Исследовательские сценарии:

1. Выборка с JOIN проекта по `project_id` и статусу с сортировкой и LIMIT.
2. Поиск по заголовку `LIKE`.
3. GROUP BY статуса.
4. UPDATE и DELETE изолированной временной записи, затем очистка фикстуры.
5. Сравнение выборки до и после исследуемого составного индекса и план выполнения.
6. COMMIT двух связанных записей с проверкой сохранения.
7. ROLLBACK вставки проекта с проверкой отсутствия строки.
8. Для WASM — закрытие и повторное открытие базы, проверка количества задач.

Для временных SQL-запросов сценарии выполняют один прогревочный вызов и от 1 до 20 измеряемых повторов (по умолчанию 5). Backend возвращает среднее, медиану, минимум/максимум и число повторов; API-время и время браузерного вызова показываются отдельно. Для массовой вставки UI измеряет полную операцию; сервер возвращает время серверной вставки, browser worker аккумулирует время непосредственно вызовов SQLite. Время подготовки WASM/открытия OPFS записывается в окружение запуска. Для серверных транзакций измеряется полное время сценария вместе с подключением и проверками; отдельно SQL-время там не заявляется. Накладные расходы сериализации, планировщика и Worker не следует интерпретировать как SQL-время.

SQLite-план измеряется через `EXPLAIN QUERY PLAN`. PostgreSQL возвращает `EXPLAIN` без `ANALYZE`, чтобы не включать второе фактическое исполнение в измеряемый запрос. Индексы могут ускорять чтение ценой скорости записи и дискового пространства.

## Интерпретация

Результат фиксирует режим, дату, seed, объём данных и повторы. История хранится в памяти UI текущей сессии; для длительного архива экспортируйте её в CSV/JSON. Достоверные метрики CPU/RAM процесса backend, размера серверной БД и размера OPFS-файла прототип не собирает; нечисловые подстановки не используются. На измерения влияют CPU, память, диск, ОС, версии СУБД/браузера, состояние кэша, сеть и параллельная нагрузка. Сравнивайте SQL-время отдельно от задержки UI; результаты не доказывают, что одна технология всегда быстрее. Прототип не моделирует конкурентную многопользовательскую нагрузку.
